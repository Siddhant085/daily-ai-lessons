Grounding Actions to Pixels

How VLM-based computer-use agents turn "click the Save button" into (x, y) — Lesson for Siddhant · Oct 11, 2026

1. Intuition first

A computer-use agent has two jobs: decide what to do (planning) and say exactly where (grounding). Planning is language; grounding is geometry. LLMs are great at the first and historically bad at the second because their output is a token stream, not a spatial pointer. Every grounding approach is a way to bridge "text out" to "point on screen" — either by giving the model labels to name (element IDs), or by teaching it to write coordinates as text.

2. The problem

Input: screenshot I (W×H) + instruction q (+ history). Output: an action like click(x,y), type("..."), or click(element_17). Success (in benchmarks) = predicted point falls inside the target element's bounding box. Small targets, dense UIs, and huge screens make this hard.

4. Approaches

A. Element IDs: Set-of-Marks & accessibility trees

Overlay numbered boxes on detected elements (Set-of-Mark prompting; or a parser like OmniParser), or serialize the DOM/accessibility tree, and have the model output an ID. The harness maps ID → box center. Pros: exact clicks, works with general VLMs, no coordinate training. Cons: depends on the detector/a11y tree (canvas apps, games, custom widgets, remote desktops often have none); marks occlude content; long trees blow context.

B. Direct coordinate prediction as text

The model emits numbers as tokens: click(512, 300). Choices that matter:

  • Normalized vs absolute. Normalized: SeeClick emits [0,1] ratios with two decimals; Qwen-VL and Qwen2-/Qwen3-VL use a relative 0–1000 grid is resolution-invariant. Absolute pixels (Qwen2.5-VL is commonly described as switching to absolute coordinates in the resized image's pixel space — check your model's docs; Anthropic's computer-use tool works in the declared display's pixel space) are more literal but tie the output to a specific image size.
  • Tokenization. "1" "2" "3" digit tokens vs whole-number tokens vs dedicated location tokens (e.g. <loc_123> bins). Digit-level outputs have no notion of numeric distance in the loss: predicting 499 vs 500 costs as much as 900 — one reason RL / distance-aware rewards have become popular for grounding.
  • Resolution & tiling. Models see a resized or tiled image (e.g. dynamic-resolution patching). A 4K screen downscaled to ~1300px wide shrinks a 16px icon to ~5px — below one vision patch. Tiling/cropping preserves detail but you must map tile-local coords back to global ones.

C. Hybrids & search

Coarse-to-fine zoom: predict a region, crop, re-ground (e.g. ScreenSeekeR on ScreenSpot-Pro). Planner+grounder split: a strong LLM writes "the blue Export button in the top-right toolbar", a specialist grounder (SeeClick, OS-Atlas, UGround, UI-TARS) outputs the point.

6. Worked example

Screen 2560×1600. Harness resizes to 1280×800 (scale 0.5). Target "Save" box in real pixels: x∈[2160,2496], y∈[144,248].

  1. Model sees Save at ~x∈[1080,1248], y∈[72,124]; emits click(1164, 98) (input-image pixels).
  2. Normalized equivalent: (1164/1280, 98/800) = (0.909, 0.1225) — identical for any resolution.
  3. Correct mapping: (0.909·2560, 0.1225·1600) = (2328, 196) ✓ inside the box.
  4. Bug — forgot to rescale: click at (1164, 98) on the real screen → lands mid-toolbar, ~1164px left of target. ✗
  5. Small-target sanity check: a 32px icon on the real screen is 16px in the model image (~0.6 of a 28px ViT patch). A ±10px model error is ±20px on screen — larger than the icon. This is why ScreenSpot-Pro scores are so much lower than ScreenSpot.

7. Training data sources

  • Web crawls: render pages, take DOM element boxes + text/alt/aria labels → (screenshot, referring expression, box). Cheap and huge (SeeClick, UGround, OS-Atlas).
  • Mobile: Android view hierarchies / accessibility metadata (e.g., RICO, AITW-style datasets).
  • Desktop: accessibility APIs on Windows/macOS/Linux via automated exploration (OS-Atlas toolkit).
  • Synthetic referring expressions: LLMs rewrite element metadata into natural, functional or positional descriptions ("the button to the left of Cancel").
  • Agent trajectories: human or model demonstrations; online RL rollouts in VMs (UI-TARS, CUA).

8. Benchmarks

  • ScreenSpot (SeeClick): 1,200+ instructions on 600+ screenshots across iOS/Android/macOS/Windows/web, text vs icon targets. Largely saturated by 2025 models.
  • ScreenSpot-v2: cleaned annotations.
  • ScreenSpot-Pro: 1,581 instructions, 23 professional apps, 5 industries, 3 OSes, high-res with tiny targets; best baseline at release (OS-Atlas-7B) only 18.9%, ScreenSeekeR visual search 48.1% training-free.
  • End-to-end: OSWorld, WebArena, AndroidWorld measure task success where grounding is one failure source.

9. Common failure modes

  • Rescale / aspect / DPI mismatch (HiDPI: logical vs physical pixels on macOS ×2!).
  • Tiny icons lost after downscaling; icon-only targets far worse than text targets.
  • Off-by-element: clicks the label next to the checkbox, or the neighbor in a dense toolbar.
  • Ambiguity: two "OK" buttons; model picks the wrong one with high confidence.
  • Stale screenshot: UI moved (animation, scroll, popup) between capture and click.
  • Hallucinated targets: element doesn't exist (benchmarks with negative instructions test refusal).
  • Domain shift: pro apps (CAD, IDEs, DAWs) differ from web-trained data.

10. Practical tips

  • Own one coordinate contract: log raw model output, image size sent, screen size, scale factors on every action. Unit-test the round trip.
  • Preserve aspect ratio; if you pad, subtract the padding offset before scaling.
  • Use a11y/DOM IDs when available, pixels as fallback — hybrid beats either alone on messy apps.
  • Zoom-in for small targets: crop around the first guess and re-ground at higher effective resolution.
  • Verify after acting: take a screenshot, check expected state change; retry with a refined description.
  • Evaluate on ScreenSpot-Pro-like slices from your target apps, split text vs icon.
  • For training, consider distance-aware rewards (RL on hit/miss or distance) instead of only token CE on digits.

11. Key takeaways

  1. Grounding = turning a description into a point; it's separable from planning and often handled by a specialist.
  2. Element IDs are exact but depend on structure; coordinate tokens are universal but noisy.
  3. Normalized coords decouple output from resolution; the #1 production bug is still scale mapping.
  4. Downscaling kills small targets — high-res benchmarks (ScreenSpot-Pro) expose this; crop/zoom helps.
  5. Close the loop: verify each action from the next screenshot.
