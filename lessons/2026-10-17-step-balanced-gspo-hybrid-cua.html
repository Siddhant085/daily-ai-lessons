Step-balanced GSPO: who gets the gradient when a GUI agent can also write code

Track: latest · Lesson for Siddhant · Oct 17, 2026 · ~15 min · Main paper: OS-Helix (arXiv:2610.22234, submitted Oct 15, 2026)

Learning objectives. By the end you should be able to:
  • Write the importance ratio at the token (PPO/GRPO), sequence (GSPO), and action-step (Step-balanced GSPO) level, and say what each one is a ratio of.
  • Show that in a multi-action training sample, the GSPO log-ratio is a token-count-weighted average of per-step log-ratios, and derive what that does to (a) how gradient is split across steps and (b) the clipping decision.
  • Derive why Step-balanced GSPO makes each step's total gradient coefficient independent of its token length, and list what it does not fix.
  • Tell apart the two knobs in a PPO-style agent objective, the ratio aggregation unit and the advantage unit, and combine them for a hybrid GUI+code computer-use agent.

Check yourself(1) A uniform advantage can't tell useful steps from redundant ones, and process rewards changed the advantage term. Today is about the other factor, the importance ratio, and how it gets aggregated. (2) A click is a few dozen tokens including the tool wrapper. A script can be hundreds of tokens. That length gap is the whole story today. (3) Only the assistant responses generated inside the retained window go in the loss. Older tokens are conditioning with loss mask 0. OS-Helix does exactly this during RL. (4) Code turns many brittle GUI steps into one precise operation (bulk edits, file transforms), which shortens the horizon and avoids grounding small widgets.
Hook. You give your GUI agent a Python/Bash tool and run online RL with a sequence-level objective. As training goes on, the agent writes scripts for more and more of its steps, and the success rate ends up below the SFT checkpoint you started from. Nothing in the reward prefers code. So where did the push toward code come from? OS-Helix reports exactly this with standard GSPO. The cause is not the reward. It is how the loss counts tokens when one training sample contains several actions of very different lengths.

1. Setup: one policy, two kinds of actions

OS-Helix (Yang, Jin, Ding, et al., 2026) trains one multimodal policy over a unified action space:

$$a_i \sim \pi_\theta(\cdot \mid q, h_i, o_i),\qquad a_i \in \mathcal{A}_{\text{hybrid}} = \underbrace{\mathcal{A}_{\text{GUI}} \cup \mathcal{A}_{\text{meta}}}_{\mathcal{A}_{\text{native}}} \cup \mathcal{A}_{\text{code}}$$

GUI actions are clicks and keystrokes. Meta-actions end the episode, for example. Code actions run Python or Bash in a fresh process, and their stdout/stderr is appended to the context. The pipeline is SFT cold start on filtered teacher trajectories, then online RL in live Ubuntu VMs, where a rule-based evaluator score is the only reward.

Why bother with hybrid? GUI gives access to anything rendered on screen. Code gives precise, bulk manipulation of files and system state. The paper's preliminary finding: just exposing a code tool to a GUI-trained model made it slightly worse. Routing between the two has to be learned.
The asymmetry that matters today. In the serialized assistant output, a GUI step is short (reasoning, wrapper, coordinates). A code step is long (reasoning, wrapper, a script). One RL training sample (a segment of the trajectory) contains several action steps, some short and some long, that all share one outcome advantage.

2. Ratio granularity: token → sequence → step

Every PPO-family objective multiplies an advantage by an importance ratio \(\pi_\theta/\pi_{\text{old}}\) and clips the ratio to keep the update near the policy that collected the data. The ratio is needed because rollouts come from a slightly stale policy: mini-batching makes the data off-policy, and OS-Helix's asynchronous pipeline lets rollouts lag the learner by up to one version. The design question is what unit you compute the ratio over.

Token-level (PPO / GRPO)

$$\mathcal{J}_{\text{GRPO}} = \mathbb{E}\Big[\tfrac{1}{G}\sum_{i=1}^{G}\tfrac{1}{|y_i|}\sum_{t=1}^{|y_i|}\min\big(w_{i,t}\hat A_{i},\ \mathrm{clip}(w_{i,t},1\!-\!\varepsilon,1\!+\!\varepsilon)\hat A_{i}\big)\Big],\quad w_{i,t}=\frac{\pi_\theta(y_{i,t}\mid x,y_{i,

Each token has its own ratio and its own clip. Zheng et al. (GSPO, 2025) argue this is ill-posed: importance sampling corrects a distribution mismatch by averaging over many samples, but here each token's weight is based on a single draw from that token's next-token distribution. The result is noise that grows with response length and gets amplified by clipping. Their principle: the unit of the optimization objective should match the unit of reward.

Sequence-level (GSPO)

$$s_i(\theta)=\left(\frac{\pi_\theta(y_i\mid x)}{\pi_{\text{old}}(y_i\mid x)}\right)^{1/|y_i|} = \exp\!\Big(\tfrac{1}{|y_i|}\textstyle\sum_t \log w_{i,t}\Big),\qquad \mathcal{J}_{\text{GSPO}}=\mathbb{E}\Big[\tfrac1G\sum_i \min\big(s_i\hat A_i,\ \mathrm{clip}(s_i,1\!-\!\varepsilon,1\!+\!\varepsilon)\hat A_i\big)\Big]$$

This is a length-normalized geometric mean of the token ratios, with one ratio and one clip decision per response. Its gradient (unclipped) is

$$\nabla_\theta \mathcal{J}_{\text{GSPO}} = \mathbb{E}\Big[\tfrac1G\sum_i s_i\,\hat A_i\cdot \tfrac{1}{|y_i|}\sum_t \nabla_\theta\log\pi_\theta(y_{i,t}\mid\cdot)\Big]$$

so every token in sample \(i\) gets the same scalar coefficient \(s_i\hat A_i/|y_i|\). The length normalization keeps \(s_i\) in one numeric range across response lengths, so that a long response isn't up-weighted just for being long. That is the right fix when the unit is "one response to one prompt."

Concept check.

3. The hidden assumption: one sample ≠ one action

In agentic RL a training sample is a segment of a trajectory containing \(K_i\) action steps. Let \(a_{i,k}\) be the loss-bearing token positions of step \(k\) (reasoning, tool wrapper, and action content), \(\delta_{i,t}=\log w_{i,t}\), and \(N_i=\sum_k |a_{i,k}|\). Define the per-step mean log-ratio

$$\bar\delta_{i,k}=\frac{1}{|a_{i,k}|}\sum_{t\in a_{i,k}}\delta_{i,t}.$$

Regroup the GSPO log-ratio by step (Appendix E of the paper):

$$\log w^{\text{GSPO}}_i=\frac{1}{N_i}\sum_t \delta_{i,t}=\sum_{k=1}^{K_i}\underbrace{\frac{|a_{i,k}|}{\sum_j |a_{i,j}|}}_{\omega^{\text{GSPO}}_{i,k}}\ \bar\delta_{i,k}.$$

So the "sequence" ratio is a token-count-weighted vote over steps. Two consequences follow.

(a) Gradient mass follows length. In the unclipped branch every loss token gets coefficient \(A_i w_i / N_i\). Summed over step \(k\), its aggregate scalar coefficient is $$\sum_{t\in a_{i,k}}\frac{\partial L_i}{\partial \log\pi_\theta(y_{i,t})} = -A_i\,w_i\,\frac{|a_{i,k}|}{N_i}.$$ A successful 400-token code step gets about 13× the total push of a 30-token click in the same sample. The routing token is not multiplied directly. What happens is that the long action contributes many more gradient terms under the same advantage, so it has more say in the update direction.
(b) The trust region is measured on the long step. The single clip decision depends on \(\sum_k\omega_k\bar\delta_k\). If the code step's tokens have drifted, the whole sample gets clipped, and the clean GUI steps lose their gradient too. If a GUI step has drifted a lot, its tiny weight \(\omega_k\) hides it and the sample stays "in region" (my analysis, which follows directly from the decomposition). In effect, clipping guards the long modality and barely watches the short one.
Why this produces drift toward code (as the paper explains it). As training goes on, standard GSPO drifted toward code-heavy behavior, and success ended up slightly below the SFT start. OS-Helix attributes this to the token-count asymmetry: code steps dominate both the sample-level ratio and the clipping decision, so the optimization signal is dominated by code steps. The authors present it as "a source of token-length-driven drift", not a proof. The behavioral diagnostic is the fraction of actions that are code, tracked per RL update.
Concept check.

4. The fix: Step-balanced GSPO

Keep the token-level weights, the clipping structure, and the sample-level advantage. Change only the aggregation weights. Give each action type a nonnegative coefficient \(\alpha_\tau\) and set

$$Z_i=\sum_{k=1}^{K_i}\alpha_{\tau_{i,k}},\qquad \omega_{i,k}=\frac{\alpha_{\tau_{i,k}}}{Z_i},\qquad \boxed{\,w^{\text{step}}_i(\theta)=\exp\Big(\sum_{k=1}^{K_i}\omega_{i,k}\,\bar\delta_{i,k}\Big)\,}$$
$$J^{\text{clip}}_i=\min\Big(A_i\,w^{\text{step}}_i,\ A_i\,\mathrm{clip}\big(w^{\text{step}}_i,1-\epsilon_{\text{low}},1+\epsilon_{\text{high}}\big)\Big)$$

OS-Helix uses \(\alpha_{\text{GUI}}=\alpha_{\text{code}}=1\), so every step gets an equal vote whatever its length. Setting \(\alpha\propto|a_{i,k}|\) gives back plain GSPO, so this is a strict generalization.

Derivation: the step's total coefficient no longer depends on its length

For a token \(t\in a_{i,k}\), only \(\bar\delta_{i,k}\) depends on \(\log\pi_\theta(y_{i,t})\), and it does so with weight \(1/|a_{i,k}|\):

$$\frac{\partial \log w^{\text{step}}_i}{\partial\log\pi_\theta(y_{i,t})}=\frac{\omega_{i,k}}{|a_{i,k}|}\;\Rightarrow\;\frac{\partial L_i}{\partial\log\pi_\theta(y_{i,t})}=-A_i\,w^{\text{step}}_i\,\frac{\omega_{i,k}}{|a_{i,k}|}\;\Rightarrow\;\sum_{t\in a_{i,k}}(\cdot)=-A_i\,w^{\text{step}}_i\,\omega_{i,k}.$$

The per-step total is \(A_i w_i \omega_{i,k}\) and is independent of \(|a_{i,k}|\). In plain terms, a successful action is reinforced as a step, not in proportion to how many tokens it took to serialize. The per-token coefficient of a long step shrinks like \(1/|a_{i,k}|\), so its tokens share a fixed budget.

What it does not do (the paper says this explicitly). It does not equalize full parameter-gradient norms or variances across action lengths. The actual update still depends on token-specific gradient directions \(\nabla_\theta\log\pi_\theta(y_t)\), on which samples get clipped, and on how rewards correlate with modality choice. It removes a deterministic length multiplier and nothing more. Routing quality still comes from the SFT prior and from the reward.

Pseudocode (PyTorch-style)

# per sample i: logp_new, logp_old: [T] over assistant tokens
# loss_mask: [T] in {0,1}; step_id: [T] in {0..K-1} (-1 for non-loss tokens)
# step_type: [K] in {GUI, CODE}; alpha = {GUI: 1.0, CODE: 1.0}; A_i: scalar advantage
delta = (logp_new - logp_old) * loss_mask                 # token log-ratios
step_sum = scatter_add(delta, step_id, K)                 # sum_t delta per step
step_len = scatter_add(loss_mask, step_id, K)             # |a_k|
delta_bar = step_sum / step_len.clamp_min(1)              # mean log-ratio per step
a = tensor([alpha[t] for t in step_type])
omega = a / a.sum()                                       # standard GSPO would use step_len / step_len.sum()
log_w = (omega * delta_bar).sum()
w = log_w.exp()
J = torch.minimum(A_i * w, A_i * w.clamp(1 - eps_low, 1 + eps_high))
# (optional dual-clip for A_i < 0, applied exactly as in GSPO, using this w)
loss_i = -J
loss = mean_over_samples(loss_i)                          # batch: (1/B) sum_i loss_i

Implementation notes: you need per-token step ids, which means the rollout serializer has to record action boundaries and types. Malformed tool calls are split off as separate samples with reward 0 in OS-Helix, so step ids never straddle an invalid response. KL was disabled in their runs. If you add a token-level KL, weight it per step too, or token-count dependence comes back through the regularizer.

7. What the ablation shows (qualitatively)

With the same SFT start, data, sampling, reward, and budget, standard GSPO lowered OSWorld-Verified success below the SFT checkpoint and pushed the code-action rate well above the SFT level (from 27.9% to 40.0% of actions). Step-balanced GSPO improved success over SFT and kept the code-action rate close to SFT (26.1%). Two more findings put this in context. SFT accounts for most of the overall gain, and RL from the raw backbone with no SFT barely helped. RL improved Pass@3 more than Pass@1, which the authors read as RL finding more distinct successful trajectories rather than sharpening a single one. Takeaway: the RL objective's aggregation unit decided whether RL helped or hurt on top of a good SFT prior.

8. The other knob: advantage granularity (adaptive-group process rewards)

Step-balancing changes the ratio side. It still uses one outcome advantage \(A_i\) per sample, so a redundant click and the decisive script are reinforced equally. A paper from two days earlier works on the advantage side for GUI RL: Adaptive-Group Process Rewards (Shang et al., arXiv:2610.17710). This connects back to the Oct 14 lesson.

  1. A critic splits the executed trajectory into contiguous subgoal groups \(G_k\) using the instruction and the agent's own stated intents. The grouping comes from the trajectory itself, not from fixed windows or predefined milestones.
  2. An action-level critic labels each action with an execution result (Completed/Partial/Failed/Uncertain) and a contribution (Milestone … Harmful), using the screenshots and the later actions in the group. A group-level critic scores subgoal completion and contribution to the task, and a refinement pass re-scores each group with all groups in view.
  3. Combine the two levels with a product, which acts as an AND gate: \(r^{\text{pr}}_t=r^{\text{act}}_t\cdot\tilde r^{\text{group}}_{k(t)}\).
  4. Shape the GRPO advantage: \(A_{i,t}=\hat A^{\text{out}}_i+\alpha\,\hat A^{\text{pr}}_{i,t}\), where \(\hat A^{\text{pr}}\) is standardized over all steps of all trajectories in the group.

In their ablations, swapping the product for a sum, or removing either level, hurt agreement with human step labels. The intuition: under a sum, a perfectly executed action inside a harmful subgoal still gets half credit.

Synthesis (mine, not from either paper): composing the two knobs. GSPO-token (Zheng et al.) already supports per-token advantages, with \(s_{i,t}=\mathrm{sg}[s_i]\cdot\pi_\theta(y_{i,t})/\mathrm{sg}[\pi_\theta(y_{i,t})]\). A natural hybrid-CUA objective uses the step-balanced ratio as the stop-gradient multiplier and a per-step advantage \(A_{i,k}\) (outcome + process), with each step's token terms scaled by \(\omega_{i,k}/|a_{i,k}|\). Then both "how much credit" and "how much update budget" are decided per action step, which is the unit the environment actually responds to. Open questions: whether to clip per step or per sample, and whether process-reward noise (misreading small UI details is a major error category in the AGPR error analysis) interacts badly with a high-variance step-level advantage.

9. Other RL-system details in OS-Helix worth stealing

Frontier task sampling. EMA success \(\hat p_i\) per task, sampling weight \(\exp(-(\hat p_i-0.5)^2/2\sigma^2)\). Why it works: group-normalized advantages vanish when all G rollouts succeed or all fail, and Bernoulli variance \(p(1-p)\) is largest at \(p=0.5\).
Sliding-window segmentation. Keep 5–10 screenshots. On overflow, save the segment as a training sample and keep the newest 5. Only responses generated inside the window are in the loss, and the same windowing is used at inference so train and test match. This ties back to the Oct 16 KV/context-budget lesson, and it's why one "sample" holds several actions in the first place.
Invalid-action isolation. An unparsable tool call becomes its own sample with reward 0, even if the rest of the trajectory later succeeds. This stops later recovery from giving malformed actions accidental positive credit.

10. How this applies to computer-use agents

  • Audit any heterogeneous-length action space. GUI vs code is the clean example. Long type() payloads, long tool JSON, and especially variable-length reasoning per step cause the same token-weighted vote. If thinking is on, hard steps with long chains of thought will dominate the ratio and the clip in a GSPO-style objective.
  • Log by step type: share of loss tokens, clip fraction, mean \(\bar\delta\), and the modality mix per update. A rising code fraction with no reward reason is the signature failure.
  • Treat α as a prior with two sides. Lowering \(\alpha_{\text{code}}\) dampens code steps in both directions: less reinforcement when they succeed, less suppression when they fail, and less influence on clipping. It is not a penalty on code.
  • Match units across the stack. Reward per trajectory (verifier), advantage per step (process rewards), ratio per step (step-balanced), and context per window (segmentation). Inconsistent units are where hidden biases come from.
  • Grounding link (Oct 11). Code actions bypass grounding on tiny widgets. That's the upside. The downside is that they bring new failure modes (side effects, prompt injection through files), which the paper flags as deployment risks. Your safety gating should be per action type too.

11. Common misconceptions

  • "GSPO's length normalization already removes length bias." It removes bias between samples of different lengths. Inside a multi-action sample it still weights steps by token count.
  • "The routing token gets multiplied by the script length." No. Each token's coefficient is \(Aw/N\). The bias is in aggregate mass: the long step contributes many more terms.
  • "Step-balancing equalizes gradient norms across modalities." Explicitly not. It removes a deterministic length multiplier from the step's scalar coefficient. Directions and norms still differ.
  • "Drift toward code means code is better." Not necessarily. Here the drift came with lower success. Always separate reward-driven shifts from objective-driven shifts.
  • "Process rewards and ratio aggregation are interchangeable fixes." They act on different factors (advantage vs ratio) and fix different problems: which steps deserve credit vs how the update budget and trust region are split.

12. Key takeaways (one-paragraph summary)

PPO-family objectives multiply an advantage by a clipped importance ratio, and the aggregation unit of that ratio is a design choice. GRPO uses tokens. GSPO uses whole responses, which fits when one response is one rewarded unit. In agentic RL a training sample holds several actions, and GSPO's log-ratio becomes a token-count-weighted average over steps. Long actions such as scripts then soak up most of the update and control the clip decision, and OS-Helix observed this as drift toward code that ended below the SFT baseline. Step-balanced GSPO replaces token-count weights with explicit per-step weights \(\alpha_\tau/Z\), which makes each step's total gradient coefficient independent of its length while keeping GSPO's clipping. It is not a guarantee of good routing. Pair it with step-level advantages (adaptive-group process rewards) so that both credit and update budget are assigned per action step.
