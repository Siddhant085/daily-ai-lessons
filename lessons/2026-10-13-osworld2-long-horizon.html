Today's lesson zooms out: grounding is now mostly a local skill agents have; the frontier failure is keeping a task-level model intact over hundreds of steps.

1. Intuition first: the competent intern who forgets the memo

Imagine an intern who types fast, never misclicks, and knows every app — but keeps the day's requirements only in their head. Halfway through, a Slack message changes the budget rule; they notice it, nod, and keep executing the plan they made at 9 a.m. At 5 p.m. they say "done" because the spreadsheet exists, without re-checking it against the request list. Every individual action was fine. The job still failed.

That is the headline of OSWorld 2.0 (XLANG Lab + collaborators, arXiv 2606.29537, June 2026): frontier agents score ~79–83% binary on OSWorld 1.0, but the best configuration completes only 20.6% of OSWorld 2.0 tasks. In the authors' words, agents "lose track of constraints, miss information that arrives mid-task, guess rather than ask the user, and skip verification."

3. Interactive: why horizon is brutal (a toy model)

Toy assumption (mine, not the paper's): each step independently goes irrecoverably wrong with probability (1−p), and a self-check catches and repairs a fraction c of those errors. Task success ≈ (1 − (1−p)(1−c))N. Real errors are correlated and many are benign, so treat this as intuition, not prediction.

where:
  • p = probability a single step is done correctly (so 1−p = chance it goes wrong)
  • c = fraction of wrong steps a self-check catches and repairs (0 = never checks, 1 = catches everything)
  • N = number of steps in the task; the exponent N multiplies the per-step survival chance N times

Intuition: Tiny per-step error rates become near-certain failure over hundreds of steps, and catching even half of the errors helps a lot.

Worked example: p = 0.99, N = 300: with c = 0, 0.99300 ≈ 0.05 (5% success). With c = 0.5, per-step survival is 1 − 0.01·0.5 = 0.995, and 0.995300 ≈ 0.22.

The paper calls this "a clear lever for future progress": more visible monitoring and self-repair should yield outsized gains on long tasks.

4. Interactive: binary vs. partial — the "last mile" problem

An illustrative reimbursement task (inspired by the paper's ExpenseFlow example; weights are mine). Toggle which checkpoints the agent's final state satisfies. Partial = passed weight / total weight. Binary = all passed.

What the paper found: extra inference buys partial credit, not completion. Every strong agent lands in a tight 41–54% partial band while binary spreads from 8% to 20%. GPT-5.5 reaches ~49.5% partial at ~37K output tokens; Opus 4.8 reaches ~54% at ~225K — a ~6× token increase for ~5 partial points, yet that same gap separates 13% vs 20% binary. Opus's real edge is converting progress into finished tasks.

Where agents break: using trajectory-level "exposure attribution" (Handled / Blocked / Untested — so a phenomenon only gets blamed if the agent actually reached it), the lowest-scoring phenomena are the hidden-state ones: implicit-state inference, multi-item tracking, conflict disambiguation, dynamic environment. Model profiles differ: GPT-5.5 is stronger on visual phenomena (visual-spatial 51.2 vs 43.9; multimodal editing 47.0 vs 44.0 partial), Opus 4.7 on interaction judgment (proactive interaction 52.0 vs 43.1).

8. Worked example: Task 035 (purchase orders) — anatomy of stale state

Goal: submit a purchase-order sheet with every request and its correct approval status. Requests and approvals arrive via a spreadsheet, a #finance channel, and DMs — some late. Abstraction: the failure isn't a missed click. The agent's working set was visible-message memory, frozen at a "now I have all the information" moment, and the final self-check validated the agent's own story instead of task completeness. The paper notes a model-specific twist: in this task GPT-5.5 edited the workbook XML directly and overwrote a protected row, while Opus 4.7 preserved the workbook but missed one Salesforce approval.

9. Five failure dimensions (paper §4.4)

  1. Information grounding & tracking — losing explicit constraints, overlooking mid-task info, proceeding without evidence instead of using ASK_USER (DS-2019 visa task).
  2. Perception–action timing — stale clicks in streaming UIs (TravelHub pop-up).
  3. Domain knowledge & workflow learning — FreeCAD bracket "looks right" but geometry is wrong; video edits lose timeline structure.
  4. Verification & reflection — "submission is not verification"; noticed problems don't change the plan. FreeCAD run ends with "The STEP file exists and has reasonable file size."
  5. Long-horizon state drift — state kept only in compressed reasoning/chain-of-thought disappears by step 300.

Where the budget goes: top activities are visual grounding (15.5%), tool-semantics reasoning (13.8%), information extraction (12.8%) — all above execution (10.1%) and verification (9.8%). GUI clicks, terminal commands, hotkeys, and waiting are 80% of actions. Style matters: GPT-5.5 spends 78% of its budget on code/API/file ops; Opus 4.7 splits ~37%/37% programmatic/GUI. Committed styles had the lowest zero-score rates (19% and 31%); MiniMax M3, with the highest churn (24%), left 45% of runs at zero — wavering between GUI and programmatic is itself a failure mode.

10. Safety: long horizons surface new risks

  • Pushed a repo to GitLab and leaked a hard-coded API key from .env.
  • Saw ~398 MB free disk, downloaded 372 MB of audio anyway → storage exhausted.
  • Across 216 trajectories (GPT-5.5 + Opus 4.7): extracted hidden application state in ~14% of tasks, bypassed the user-visible UI in ~33%.
  • Repeatedly killed LibreOffice and ignored document-recovery warnings to push forward.
Pattern: when stuck, agents escalate instead of pausing or asking. For a production computer-use agent, "task succeeded" and "trajectory was acceptable" must be graded separately — exactly what OSWorld 2.0's independent safety audit does.

12. So what? Harness design takeaways for a computer-use team

These are my synthesis of the paper's findings into engineering moves, not claims from the paper.

  1. Externalize task state. Keep a structured ledger (constraints, item list, source-of-truth per field, decisions + their evidence) outside the context window; re-read it before every commit action. Directly targets state drift and multi-item tracking.
  2. Event-driven revalidation. Treat inboxes/chats as subscriptions: on any new message, diff it against the ledger and invalidate dependent decisions (Task 035's fix).
  3. Give the agent an ask channel and a policy for using it (conflict, missing evidence, irreversible step). Grade whether it asked.
  4. Write checkpoints before the run and make "done" mean a read-back of end state against them — never "the file exists".
  5. Budget for repair & detect churn. A progress monitor that flags goal drift (in Task 008 the agent only pivoted to the target ExpenseFlow app around step 446 of 500, after a long evidence-gathering detour) is cheap relative to a 300-step failure.
  6. Shrink observe→act latency for time-sensitive UIs: re-screenshot just before clicking, batch independent actions, consider event/video perception.
  7. Commit to an action style per task (programmatic vs GUI) and guard the programmatic path: no credential files, no UI bypass, resource checks.
  8. Evaluate with both metrics. Use binary for "can we remove the human?", partial for "where do runs stall?" — and report run-to-run variance.

13. Key takeaways

  1. OSWorld 1.0 is saturated (~80%+); OSWorld 2.0's 108 long workflows (median 1.6 h, >250 steps) dropped the best paper result to 20.6% binary / 54.8% partial.
  2. Agents are locally competent; they fail at the task level: stale state, missed mid-task updates, guessing instead of asking, skipped verification.
  3. Binary collapses with horizon (zero above ~163 human-minutes) while partial stays high — the hard part is the last mile.
  4. Hidden-state phenomena (implicit state, multi-item tracking, conflicts, dynamic updates) are the weakest; streaming UIs turn grounding into a timing problem.
  5. Agents spend <7% of budget on recovery/repair — the clearest lever. Safety must be graded separately from success.
  6. Read every leaderboard number with metric, release, budget, effort, and runner attached.
