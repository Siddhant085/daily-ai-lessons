  2. Sunday (screen grounding): why can a perfect local click still leave the task failed?
  3. OSWorld 2.0 grades ~27 weighted final-state checkpoints — what does that buy you that binary pass/fail does not?
Check yourself(1) Errors compound; state drifts; agents spend <7% of budget on recovery/repair. (2) Local action success ≠ task success — grounding gets the pixel right, but the trajectory can still miss constraints, mid-task updates, or verification. 1. Intuition first: who gets blamed at step 300?

Imagine a 300-step GUI episode. The agent clicks Save on the wrong spreadsheet at step 47, never notices, and at step 300 the grader says "fail." Under a sparse terminal reward — +1 if the final state passes, 0 otherwise — every action in the trajectory is multiplied by the same return. The wrong Save, the fifty correct clicks that followed, and the final verification skip all share identical credit (or blame). The learning signal cannot tell step 47 from step 280.

That is the temporal credit assignment problem (Sutton & Barto): given delayed reward, which past actions caused the outcome? For computer-use agents, the delay is extreme — reward arrives after hundreds of observe–act cycles — so the problem is not a footnote; it is why RL on long GUI trajectories is hard even when grounding is solved.

2. Formal MDP for computer-use

A Markov decision process (MDP) is the standard RL frame: a set of states 𝒮, a set of actions 𝒜, transition rules P (what the next state is after an action), a reward function R, and a discount γ. "Markov" means the next state depends only on the current state and action. Cast a computer-use episode as an MDP ⟨𝒮, 𝒜, P, R, γ⟩:

  • State st: screenshot It plus (compressed) history — prior actions, ledger/constraints, tool results. Partial observability is real; we treat the agent's input as st.
  • Action at: click(x,y), type(text), scroll, hotkey, or a tool call (bash, browser, ASK_USER). Discrete or continuous depending on the interface.
  • Transition: the OS/UI updates; the next screenshot is stochastic (animations, network, other apps).
  • Reward (classic sparse setup): rt = 0 for t < T, and rT ∈ {0, 1} from a binary task grader. Optionally discount γ ∈ (0,1].

Policy πθ(a|s) is the VLM/LLM agent (parameters θ). Objective:

J(θ) = Eτ ~ πθ[ G0 ]   where   Gt = Σk=tT γk−t rk
where:
  • J(θ) = the objective: expected starting return of the policy with weights θ
  • τ ~ πθ = an episode sampled by running the policy; E averages over such episodes
  • Gt = return from step t; G0 is the return of the whole episode
  • Σk=tT = add up over steps k = t, t+1, …, T
  • γk−t = discount: a reward k−t steps away is multiplied by γ that many times (γ between 0 and 1)
  • rk = reward at step k

Intuition: Training means making the average total reward per episode as large as possible, with rewards further in the future counting a bit less.

Worked example: 3-step episode with rewards r0=0, r1=0, r2=1 and γ=0.9: G0 = 0 + 0.9·0 + 0.81·1 = 0.81, G1 = 0 + 0.9·1 = 0.9, G2 = 1. With γ=1 all three equal 1 — the "single bit paints the whole trajectory" effect.

With sparse terminal reward and γ≈1, Gt = rT for every t — a single Bernoulli that paints the whole trajectory.

3. REINFORCE from first principles

3.1 What a policy is

A policy is a rule for choosing actions, written πθ(a|s): the probability of picking action a when you are in state s. It is a probability, not a single choice, because a learning agent has to try things. θ are the knobs (model weights) that set those probabilities. For an LLM/VLM agent, πθ(a|s) is literally the probability the model assigns to the action text given the screenshot and history.

πθ(a|s) = softmax(θ)a = eθa / Σa′ eθa′   (simplest case: one score θa per action)
where:
  • θa = a score ("logit") for action a; higher score → more likely
  • ex = exponential, always positive; dividing by the sum Σa′ over all actions a′ makes the probabilities add to 1

Intuition: scores go in, probabilities come out; training means adjusting the scores.

Worked example: two actions, "Save to shared drive" (S) and "Save to Desktop" (D), θ = (0, 0) → π = (0.5, 0.5). θ = (1, 0) → π(S) = e/(e+1) ≈ 0.73.

3.2 The goal: maximize expected return

Running the policy produces a random trajectory τ and a return R(τ) (total reward; in the sparse setup, 1 if the task passed, else 0). We can't control the randomness, so we maximize the average:

J(θ) = Eτ~πθ[R(τ)] = Στ pθ(τ) · R(τ)
where:
  • pθ(τ) = probability that the policy produces trajectory τ
  • R(τ) = return of that trajectory (here equal to G0 from §2)
  • Στ = sum over every possible trajectory (we will never compute it exactly — we'll sample)

Intuition: J is "success rate" when reward is pass/fail.

Worked example: one-step task: S passes (R=1), D fails (R=0). With π = (0.5, 0.5), J = 0.5·1 + 0.5·0 = 0.5; with π = (0.73, 0.27), J = 0.73.

3.3 The log-derivative trick, step by step

We want ∇θJ — the direction to move θ so J goes up. Problem: J is a sum over trajectories we can't enumerate, and the environment (the OS) isn't differentiable. The trick turns the gradient into an average we can sample.

  1. Differentiate the sum. R(τ) doesn't depend on θ (the grader just scores the outcome), so only the probabilities get differentiated:
    ∇θJ = Στ ∇θpθ(τ) · R(τ)
  2. Use the identity ∇ log p = ∇p / p (chain rule: the derivative of log x is 1/x). Rearranged: ∇p = p · ∇ log p.
    ∇θJ = Στ pθ(τ) · ∇θlog pθ(τ) · R(τ) = Eτ~πθ[ ∇θlog pθ(τ) · R(τ) ]
    A sum of "probability × something" is an expectation, so we can estimate it by running episodes and averaging.
  3. Expand the trajectory probability. pθ(τ) = p(s0) · ∏t πθ(at|st) · P(st+1|st,at). The log of a product is a sum of logs, and p(s0) and P (the OS) don't depend on θ, so their gradients are 0:
    ∇θlog pθ(τ) = Σt=0T ∇θlog πθ(at|st)
    That's why we never need to differentiate the environment.
  4. Estimate with n sampled episodes (Williams, 1992, REINFORCE):
    ∇θJ ≈ (1/n) Σi=1n Σt ∇θlog πθ(at(i)|st(i)) · R(τ(i)),    then θ ← θ + α · ∇θJ
where:
  • ∇θ = gradient with respect to the weights θ; log = natural log
  • p(s0) = chance of the start state; P(st+1|st,at) = how the OS responds; ∏t = product over steps
  • n = number of sampled episodes; superscript (i) = "from episode i"; α = learning rate (step size, e.g. 0.1)
  • ∇θlog πθ(a|s) = "score function": the direction in weight space that makes action a more likely in state s

Intuition (the whole algorithm in one sentence): after each episode, raise the log-probability of every action you took, in proportion to the return the episode got. Good episodes make their actions more likely; zero-return episodes change nothing; (with negative returns) bad episodes make their actions less likely.

Causality refinement: an action can't affect rewards that came before it, so R can be replaced by Gt (reward from step t on), giving ∇J = E[Σt ∇ log π(at|st) · Gt]. Same expectation, slightly less noise. With a single terminal reward, Gt = R for every t, so it doesn't help here.

3.5 Why sparse terminal reward makes REINFORCE slow

  • Everyone shares one R. Every step's gradient is ∇ log π(at|st) × the same number. The only thing distinguishing the bad step from the fine ones is a correlation between its action and R, which has to emerge statistically over many episodes.
  • Buried in noise. In each episode, the other steps' random choices also change R (and also add their own ±score terms to the gradient). For the step you care about, that's noise: the step's signal is the average difference in R between its good and bad choice; the noise is everything else that moves R.
  • Grows with horizon. More steps → more independent sources of failure → success becomes rarer (here 0.9N−1), so most episodes give R = 0 and no signal at all; the episodes that do succeed are a smaller fraction. In the widget below, the episodes needed to single out one bad step grow roughly like 1/0.9N — exponentially in horizon. Real agents have far more than two choices per step and correlated failures, which makes it much worse.

3.7 The fix this motivates: baselines and advantages

The widget shows the problem is noise, not a wrong direction (and that even dense rewards are useless if you multiply by raw, noisy returns): the gradient is correct on average but needs too many samples. Two cures, both developed next:

  • Baseline: subtract a number b from R before multiplying. If b is "what you usually get", then success episodes push up (R − b > 0) and failures push down (R − b < 0), so failure B in the table above finally says "make these actions less likely." It provably doesn't change the average gradient (derivation below) but cuts variance.
  • Advantage: make the baseline state-dependent, At = Gt − V(st): "was this step's outcome better than expected from here?" Combined with denser rewards (§7), it localizes blame to the step that caused it.

Worked example: in the 3-step table, the average return is b = 0.9·0.5·0.9 ≈ 0.405. In episode B, step 2 chose bad, so its score term on the "good" logit is −0.5; times (R − b) = −0.405 gives +0.20: raise the "good" score, i.e. make the bad choice less likely. Without the baseline that episode contributed 0.

Mini derivation: why a state-independent baseline does not bias the gradient E[∇ log πθ(a|s) · b(s)] = Σa π(a|s) ∇ log π(a|s) · b(s) = b(s) ∇ Σa π(a|s) = b(s) ∇(1) = 0. So subtracting any function of s alone (or a constant) leaves ∇J unbiased while typically cutting variance. That is the door to baselines and advantages below.
where:
  • b(s) = baseline: any number that depends only on the state (not the action)
  • Σa π(a|s) … = average over the actions the policy might pick in s
  • π ∇ log π = ∇π (since ∇log x = ∇x / x)
  • Σa π(a|s) = 1, because probabilities sum to one; the gradient of a constant is 0

Intuition: Because action probabilities always sum to 1, pushing some up must push others down, so a shift that is the same for every action averages out to zero.

Worked example: Two actions with π=0.7 and 0.3. Nudge θ so π becomes 0.75/0.25: ∇π = +0.05 and −0.05. Times b=5: 0.25 − 0.25 = 0. The baseline adds nothing on average.

4. Interactive: horizon, discount, sparsity → learning signal

Toy model (mine, for intuition — not a theorem). Each step emits an independent reward with probability sparsity pr (else 0); when it fires, the magnitude is ±1 with equal chance. Return G0 = Σt=0N−1 γt rt. We plot: (i) std of G0 across rollouts, (ii) a crude "signal-to-noise" proxy |E[G0]| / (std(G0)+ε) when we inject a small systematic +δ bias on rewards (simulating a slightly better policy). Watch what happens as N grows and as you make rewards rarer.

where:
  • N = horizon (number of steps); pr = chance a step emits a nonzero reward
  • rt = +1 or −1 when it fires (50/50), else 0; γ = discount
  • std(G0) = how much the return varies between rollouts (noise)
  • δ = a small extra average reward from a slightly better policy (here 0.05); ε = tiny number to avoid dividing by 0
  • SNR = |E[G0]| / std: how visible the improvement is above the noise

Intuition: More random reward terms add more noise than the small improvement adds signal, so long horizons drown the learning signal.

Worked example: γ=1, pr=1: Var(G0) ≈ N (each step adds variance ≈1). N=4 → std≈2; mean = 4·0.05=0.2; SNR≈0.1. Mean signal grows like N·pr·δ while std grows like √(N·pr), so small pr (rare rewards) is what crushes SNR: N=100, pr=1 → SNR = 5/10 = 0.5; pr=0.03 → mean 0.15, std≈1.73, SNR≈0.09. With γ<1, extra steps beyond ~1/(1−γ) add almost nothing.

5. Baselines and advantage

Replace Gt with an advantage:

At = Gt − b(st)  ≈  Gt − Vπ(st)
where:
  • At = advantage of the action at step t
  • Gt = return actually obtained from step t
  • b(st) = baseline for that state; the best common choice is Vπ(st)
  • Vπ(s) = expected return from state s when following π (a learned estimate in practice)

Intuition: Judge an action by whether things went better or worse than usual from that situation, not by the raw score.

Worked example: 3 steps, rewards [0,0,1], γ=1 → G = [1,1,1]. Value estimates V = [0.4, 0.6, 0.9] → A = [0.6, 0.4, 0.1]. Early steps get more credit because success was less expected there; had the episode failed (G=[0,0,0]), A = [−0.4, −0.6, −0.9].

Vπ(s) = E[Gt | st=s] is the expected return from s. Then At asks: did this action do better or worse than average for this state?

  • Unbiased: as shown above, any b(s) (or constant) has expectation zero against ∇ log π.
  • Lower variance: Gt and V(st) are correlated; subtracting removes shared noise. A good baseline is the biggest free lunch in policy gradients.
  • Still smeared under sparse rewards: if Gt = rT for all t, then At = rT − V(st). Early states with similar V still get nearly identical advantages when rT is the only signal — baselines help, but they do not invent intermediate credit.

Actor-critic trains a critic Vφ alongside the actor πθ, and uses Vφ(st) as the baseline (or bootstraps one-step TD: δt = rt + γ V(st+1) − V(st)).

where:
  • Vφ = critic: a value network with its own weights φ
  • δt = TD (temporal-difference) error: reward now + discounted value of the next state − value of this state

Intuition: δt is the one-step surprise: did this step leave you better off than the critic predicted?

Worked example: V(s0)=0.4, step gives r0=0 and lands in s1 with V=0.6, γ=1 → δ0 = 0 + 0.6 − 0.4 = +0.2: the action looked good even before any real reward.

6. GAE intuition (λ-return) — without a full PPO tutorial

Schulman et al. (2016) introduced Generalized Advantage Estimation. Define the TD residual δt = rt + γ V(st+1) − V(st). Then:

ÂtGAE(γ,λ) = Σl=0∞ (γλ)l δt+l
where:
  • ÂtGAE(γ,λ) = estimated advantage at step t (hat = estimate)
  • δt+l = TD error l steps later (defined just above)
  • l = how many steps ahead; Σl=0∞ sums to the end of the episode (δ = 0 after it)
  • γ = discount; λ ∈ [0,1] = how much to trust later TD errors vs the critic

Intuition: Add up the upcoming one-step surprises, fading them by (γλ) each step: λ near 0 trusts the critic, λ near 1 trusts the real rewards.

Worked example: Rewards [0,0,1], V = [0.4,0.6,0.9], γ=1, V after end = 0. δ = [0.2, 0.3, 0.1]. λ=0: Â0=0.2. λ=1: Â0=0.2+0.3+0.1=0.6 = G0−V(s0). λ=0.5: 0.2 + 0.5·0.3 + 0.25·0.1 = 0.375.

  • λ = 0: Ât = δt — pure 1-step TD. Low variance, high bias (depends heavily on V).
  • λ = 1: Ât = Gt − V(st) — Monte Carlo advantage. Low bias, high variance.
  • λ ∈ (0,1): exponential mix of n-step advantages — the bias–variance dial used in modern on-policy LLM-RL (PPO/GRPO-style trainers almost always sit on GAE or a close cousin).

For computer-use: GAE helps when you have some intermediate reward structure or a decent value model. It does not magically solve a 300-step episode with a single terminal bit — you still need denser targets or a critic that has learned long-horizon value (itself hard).

7. Process rewards vs outcome rewards

Outcome reward (ORM-style): grade only the final answer / final UI state. One scalar for the whole trajectory.
Process reward (PRM-style): grade intermediate steps — each reasoning step, or each GUI checkpoint.

Lightman et al. ("Let's Verify Step by Step", 2023) showed that process supervision significantly outperforms outcome supervision for training reward models on MATH: step-level labels give a denser, more local training signal and reduce "right answer, wrong reasoning." The same logic transfers to agents:

  • OSWorld 2.0's ~27 weighted final-state checkpoints are a form of process-shaped evaluation: they tell you which subgoals held, not just pass/fail. Used as training rewards (or as shaping), they turn one Bernoulli into a vector of subgoal successes.
  • Step-level / checkpoint rewards shrink the effective credit horizon: an action that completes "attach receipt" gets credit at that checkpoint, not only at episode end.
  • Trade-off: process rewards can be misspecified (reward hacking on the proxy), expensive to label, and may encourage myopic subgoal-chasing. Outcome rewards are aligned with the true goal but starve the learner of signal.

For GUI RL, practical densification patterns include: checkpoint matchers on DOM/file state, progress heuristics (form fields filled), PRM-style judges on action traces, and verification tools that emit intermediate ± scores.

9. Connecting the dots for computer-use training

Engineering synthesis — not a claim from any single paper.

  1. Sparse terminal RL alone is a poor fit for 300-step GUI tasks. REINFORCE variance and smeared credit make learning sample-hungry even when local grounding is good (Sunday's lesson).
  2. Baselines / GAE are necessary but not sufficient. They cut variance; they do not create intermediate targets. Pair them with denser rewards or a strong critic.
  3. Process rewards / checkpoints reshape the credit landscape — the same reason OSWorld 2.0's partial scoring reveals "last mile" failures that binary hides, and the same reason PRMs beat ORMs on multi-step math.
  4. Don't confuse eval checkpoints with reward shaping. Using the grader's internals as training reward can overfit to the benchmark; prefer independently specified subgoals or learned PRMs.
  5. Recovery behavior needs its own credit. Yesterday: agents spend <7% budget on repair. If only final success is rewarded, repair actions that don't change the terminal bit get no learning signal — consider explicit rewards (or preferences) for verified fixes.

10. Key takeaways

  1. Temporal credit assignment asks which past actions caused a delayed outcome — the central difficulty of RL on long computer-use trajectories.
  2. REINFORCE: ∇J = E[Σt ∇ log π(at|st) · Gt]. With sparse terminal reward, Gt is the same random bit for every t → high variance, smeared credit.
  3. Subtracting a state-value baseline does not bias the gradient; advantages At = Gt − V(st) cut variance.
  4. GAE(γ,λ) interpolates TD and Monte Carlo advantages — the bias–variance dial behind modern on-policy LLM-RL.
  5. Process/step rewards densify credit (PRMs; OSWorld-style checkpoints). They help learning but must be designed to avoid reward hacking.
  6. Local action success ≠ task success: grounding can be perfect while credit assignment still fails the long job.
